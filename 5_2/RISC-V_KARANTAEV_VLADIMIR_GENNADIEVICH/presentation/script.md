# Зачем нужны РТОСки?

RTOS редко является обязательным требованием; однако по мере того, как вы
начинаете расширять функциональность своих встроенных приложений, становится
все труднее выполнять все действия в рамках одного основного цикла и некоторых
процедур прерывания. Обычно следующий уровень сложности - это своего рода
конечный автомат, в котором выходные данные вашего электронного устройства
изменяются в зависимости от этого (внутреннего) состояния. Дальше двигаться некуда.
Например, что, если вам нужно иметь возможность управлять несколькими сложными
входами и выходами одновременно? Хорошим примером может служить соединение по
протоколу TCP/IP, по которому вы будете получать какие-то данные, которые затем
должны использоваться для управления роботизированной рукой, управления
электродвигателем, отправки сигнала... Быстро становится ясно, что требуется
новый уровень абстракции, чтобы не утонуть в сложности, которая потребовалась
бы для реализации чего-то подобного. И тут на помощь приходит RTOS.

# Зачем RTOS?

Первая и самая фундаментальная часть RTOS -
это ядро. Ядро отвечает за планирование процессорного времени для каждой
конкретной задачи таким образом, чтобы казалось, что они выполняются
одновременно. Подробности о том, как работает этот алгоритм планирования (или,
как его еще называют, scheduler), на данный момент не важны.

Каждый поток (или задача) при выполнении будет использовать регистры и память.
Все эти регистры процессора и стек (память) нарушают контекст этого конкретного
потока. Как только RTOS решит переключить поток и запустить что-то еще, ей
нужно будет сначала сохранить контекст, а затем загрузить контекст для потока,
который она хочет запустить следующим. Этот процесс называется переключением
контекста.

Наряду с потоками, вы будете использовать такие примитивы, как очереди,
мьютексы и семафоры для взаимодействия между потоками. Затем каждая RTOS
обеспечивает различные уровни поддержки различных протоколов, таких как TCP/IP,
Bluetooth... Это упрощает вашу жизнь, так как теперь вам не нужно так
глубоко изучать эти протоколы. Вы получите серию вызовов API, которые должны
увеличить скорость разработки.

# yadro

Ядро Zephyr лежит в основе каждого приложения Zephyr. Оно обеспечивает
малозатратную, высокопроизводительную многопоточную среду выполнения с богатым
набором доступных функций. Остальная часть экосистемы Zephyr, включая драйверы
устройств, сетевой стек и код для конкретных приложений, использует возможности
ядра для создания полноценного приложения.

Конфигурируемый характер ядра позволяет вам включать только те функции, которые
необходимы вашему приложению, что делает его идеальным для систем с
ограниченным объемом памяти (всего 2 КБАЙТ!) или с простыми требованиями к
многопоточности (такими как набор обработчиков прерываний и одна фоновая
задача). Примерами таких систем являются: встроенные сенсорные концентраторы,
датчики окружающей среды, простые светодиодные носимые устройства и бирки для
инвентаря магазинов.

Приложения, требующие большего объема памяти (от 50 до 900 КБ), нескольких
устройств связи (таких как Wi-Fi и Bluetooth с низким энергопотреблением) и
сложной многопоточности, также могут быть разработаны с использованием ядра
Zephyr. Примерами таких систем являются: носимые устройства для фитнеса, умные
часы и компьютер автомобиля.

Ядро модульное и состоит из ряда сервисов.

# Поток

## Что это?

Поток - это изолированный экземпляр, который отвечает за выполнение некоторой
задачи. В то время как микроконтроллер обычно имеет только 1 центральный
процессор, RTOS может выполнять несколько задач (по-видимому) одновременно,
заменяя поток, который запускается на центральном процессоре в соответствии с
указаниями планировщика.


Область стека: область памяти, используемая для стека потока. Размер может быть
изменен в соответствии с требованиями процесса обработки потока.
/* size of stack area used by each thread */
#define STACKSIZE 1024

Блок управления потоком: для внутреннего учета метаданных потока. Экземпляр типа k_thread.
k_thread_stack_define(THREAD_A_STACK_AREA, stacksize);
STATIC STRUCT K_THREAD THREAD_A_DATA;


Функция точки входа, которая вызывается при запуске потока. Этой функции может быть передано до 3 значений аргументов.

/* thread_a is a dynamic thread that is spawned in main */
void thread_a_entry_point(void *dummy1, void *dummy2, void *dummy3)
{
	ARG_UNUSED(dummy1);
	ARG_UNUSED(dummy2);
	ARG_UNUSED(dummy3);

	/* invoke routine to ping-pong hello messages with thread_b */
	hello_loop(__func__, &thread_a_sem, &thread_b_sem);
}

Параметр ARG\_UNUSED необходим, чтобы указать, что эти 3 аргумента не используются в нашей функции thread.

    Политика планирования: указывает планировщику ядра, как распределять
    процессорное время для потока. (Это будет рассмотрено в разделе
    Планирование) Режим выполнения: может быть режимом супервизора или
    пользователя. По умолчанию потоки выполняются в режиме супервизора и
    предоставляют доступ к привилегированным командам процессора, всему
    адресному пространству памяти и периферийным устройствам. Потоки
    пользовательского режима имеют ограниченный набор привилегий.

 Набор параметров потока, которые позволяют ядру обрабатывать поток особым
 образом при определенных обстоятельствах.

# Планировщик

Планировщик основан на приоритетах ядра, позволяет потокам приложения совместно использовать центральный процессор.

Существуют различные моменты времени, когда планировщику предоставляется
возможность изменить идентификатор текущего потока, то есть когда планировщик
переключает выполнение ЦП с одного потока на другой. Эти моменты называются
точками изменения расписания. Некоторые потенциальные точки изменения
расписания являются:

    переход потока из запущенного состояния в состояние приостановки или
    ожидания, например, с помощью k_sem_take() или k_sleep().

    перевод потока в состояние готовности, например, с помощью k_sem_give() или
    k_thread_start()

    возврат к контексту потока после обработки прерывания

    когда запущенный поток вызывает функцию k_yield()

Поток переходит в спящий режим, когда он добровольно инициирует операцию,
которая переводит его в состояние приостановки или ожидания.

Всякий раз, когда планировщик изменяет идентификатор текущего потока или когда
выполнение текущего потока заменяется ISR, ядро сначала сохраняет значения
регистров процессора текущего потока. Эти значения регистров восстанавливаются,
когда поток позже возобновляет выполнение.


c_idle.c
Перевести процессор в режим ожидания просто: вызовите API k_cpu_idle().
Процессор прекратит выполнение инструкций до тех пор, пока не произойдет
событие. Скорее всего, функция будет вызвана в цикле. Обратите внимание, что в
некоторых архитектурах при возврате функция k_cpu_idle() безоговорочно
отключает прерывания.


Планировщик делит время на ряд временных интервалов, которые
измеряются в тактах системных часов. Размер временного интервала
настраивается, но его можно изменить во время работы приложения.

В конце каждого временного интервала планировщик проверяет, является ли текущий
поток доступным для выгрузки, и, если это так, неявно вызывает k_yield() от
имени потока. Это дает возможность другим готовым потокам с таким же
приоритетом выполняться до того, как текущий поток будет запланирован снова.
Если ни один из потоков с таким же приоритетом не готов, текущий поток
остается.

Потоки с приоритетом, превышающим указанный предел, освобождаются от
преимущественного сокращения времени и никогда не будут вытеснены потоком с
равным приоритетом. Это позволяет приложению использовать преимущественное
сокращение времени только при работе с потоками с более низким приоритетом,
которые менее чувствительны ко времени.

Примечание: алгоритм разделения времени ядра не гарантирует, что набор потоков
с равным приоритетом получит равное количество процессорного времени, поскольку
он не измеряет количество времени, которое поток фактически получает на
выполнение. Однако алгоритм гарантирует, что поток никогда не будет выполняться
дольше одного временного интервала без необходимости получения результата.

Вытесняемый поток, который не хочет, чтобы его вытесняли при выполнении
критической операции, может дать команду планировщику временно рассматривать
его как совместный поток, вызвав функцию k_sched_lock(). Это предотвращает
вмешательство других потоков во время выполнения критической операции.

Поток может вызвать функцию k_sleep(), чтобы отложить свою обработку на
определенный период времени. В течение времени, пока поток находится в спящем
режиме, центральный процессор освобождается для выполнения других готовых
потоков. Как только указанная задержка истекает, поток становится готовым и
может быть запланирован еще раз.

Спящий поток может быть преждевременно разбужен другим потоком с помощью
функции k_wakeup(). Иногда этот метод может использоваться для того, чтобы
позволить вторичному потоку сигнализировать спящему потоку о том, что что-то
произошло, не требуя от потока определения объекта синхронизации ядра, такого
как семафор. Пробуждение потока, который не находится в спящем режиме,
разрешено, но не имеет никакого эффекта.


# Memory

Встраиваемые системы используют иерархическую архитектуру памяти,
оптимизированную с точки зрения производительности, энергопотребления и
ограничений по стоимости:

Основные типы памяти

Статическая оперативная память (SRAM)

    Основная рабочая память для выполнения операций в рантайме
    Максимальная скорость доступа с минимальной задержкой
    Ограниченный объем (обычно в диапазоне от КБ до Мбайт)
    Содержит системную кучу, стеки потоков и глобальные переменные
    Адресуемые непосредственно процессором

Флэш-память

    Энергонезависимое хранилище для программного кода и констант
    Возможности Execute-in-place (XIP) снижают требования к SRAM
    Увеличенная емкость, но значительно более медленные операции записи
    Организация по секторам/страницам для эффективного управления

Кэш-память

    Высокоскоростной буфер между процессором и основной памятью
    Кэширование команд и данных повышает производительность выполнения
    Программирование с поддержкой кэширования повышает эффективность системы
    Критически важно для высокопроизводительных встраиваемых приложений
