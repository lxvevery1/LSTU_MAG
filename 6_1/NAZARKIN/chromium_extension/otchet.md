# Отчёт о выполненной работе

**Проект:** браузерное расширение для классификации постов r/WallStreetBets
**Каталог:** `6_1/NAZARKIN/chromium_extension/`
**Дата:** 2 октября 2026
**Статус:** работает, проверено в Firefox вручную и в Chrome автоматически

---

## 1. Задача

Сделать расширение, которое у каждого видимого поста в r/WallStreetBets показывает
бейдж с классификацией по уже обученной модели, используя существующую локальную
модель из `wsb_classification/`. Расширение должно работать и в Chromium, и в Firefox,
классифицировать как страницу отдельного поста, так и ленту подписки.

---

## 2. Что получилось

Расширение показывает у каждого поста цветной бейдж с меткой и вероятностью,
например `analysis · 0.62`. При наведении — подробная подсказка с распределением
вероятностей по всем классам и указанием источника текста. Метки кэшируются, поэтому
повторные просмотры мгновенные.

Работает в Firefox (проверено вручную: расширение загружено через отладку, посты
классифицируются) и в Chromium (проверено автоматически в реальном Chrome, 9 групп
проверок).

## 3. Компоненты

| Файл | Размер | Назначение |
|---|---|---|
| `manifest.json` | 1,0 КБ | MV3-манифест, общий для Chrome и Firefox |
| `content.js` | 16,6 КБ | Поиск постов в DOM, очередь, отрисовка бейджей |
| `background.js` | 13,5 КБ | Сетевые запросы, кэш, маршрутизация сообщений |
| `content.css` | 2,0 КБ | Оформление бейджей, стиль «неуверенно» |
| `options.html` / `options.js` | 3,1 + 3,1 КБ | Настройки, проверка модели, очистка кэша |
| `api_model/` | 42 МБ | Локальный сервер модели, `model.joblib` 8,6 МБ |
| `pickle_classification_for_learning.json` | 4,9 МБ | Размеченный датасет для проверки |
| `tools/` | 5 файлов | Тестовые harnesses (описаны в разделе 6) |

**`manifest.json`.** В секции `background` объявлены **и** `service_worker`, **и**
`scripts`: Firefox требует `scripts`, Chromium требует `service_worker`, и оба
требования выполняются одним манифестом. В `host_permissions` внесены
`127.0.0.1:8000/*` и `arctic-shift.photon-reddit.com/*`.

**`content.js`.** Работает в изолированном мире страницы, видит DOM Reddit. Ищет посты
в два прохода: сначала по известным элементам (`shreddit-post`), затем резервным поиском
по якорям-пермалинкам — на случай, если Reddit поменяет разметку. Накапливает найденное
в очередь и отправляет пачкой раз примерно в 700 мс. Состояния бейджа:
`pending` → `ok` / `error` / `empty`.

**`background.js`.** Единственное место, откуда ходят сетевые запросы — это снимает
проблему CORS к архиву. Содержит кэш в `chrome.storage.local`, нормализацию текста,
батчинг и маршрутизацию сообщений.

**`options.html` / `options.js`.** Базовый URL модели, URL архива, порог уверенности,
список подписок, кнопки «проверить модель» и «очистить кэш», счётчик записей в кэше.

## 4. Принятые технические решения

### 4.1. Порт вместо `sendMessage`

Одноразовый `chrome.runtime.sendMessage` в MV3-воркер **на этой сборке Chrome не
работает вообще** — возвращает «message port closed before a response was received».
Это проверено на отдельном трёхстрочном контрольном расширении, в Chrome, запущенном
вручную и подключённом по CDP, то есть это не артефакт тестового окружения.

Поэтому обмен между content script и фоном переведён на долгоживущий порт
`chrome.runtime.connect`. Это работает надёжно и даёт дополнительный выигрыш: открытый
порт не даёт воркеру выгрузиться между запросами. Обработчик `sendMessage` в фоне
оставлен как запасной путь для браузеров, где он работает.

### 4.2. Таймаут накрывает и чтение тела ответа

Архив Arctic Shift наблюдаемо отдаёт `200`, а затем зависает на середине тела ответа.
`fetch()` на этом резолвится уже по заголовкам — если снять таймер в этот момент,
`res.text()` будет ждать бесконечно. Таймаут держится-armed через всё чтение тела.

### 4.3. Короткий бюджет на архив + запасной источник текста

Архив нестабилен по задержке: один и тот же запрос отвечал и за 0,6 с, и за 20+ с без
воспроизводимой причины. Поэтому архиву выдан отдельный короткий бюджет (6 с), а всё,
что он не успел, классифицируется по тексту, уже присутствующему на странице.
Медленный архив даёт худшую метку, но не «нет ответа». Бейдж при этом честно
различает «архив недоступен» и «поста нет в архиве».

### 4.4. Нормализация текста строго как при обучении

Реализовано `" ".join(s.split())` — схлопывание пробельных последовательностей.
Markdown, ссылки и кавычки **не вырезаются**: в обучающих данных они присутствовали,
и их удаление сдвинуло бы распределение входа модели.

### 4.5. Батчинг

Все видимые посты ленты уходят **одним** запросом `/predict`, а не по одному на пост.
Лента из 25 постов — это 1 сетевой запрос и один `predict_proba` на 25 строк.

### 4.6. Кэш

`chrome.storage.local`, ключ `c:<id>`, TTL 7 дней. Кэш инвалидируется, если заголовок
поста изменился после кэширования — так редактированные посты переклассифицируются.
Результат повторного открытия страницы — **353 мс** вместо повторной классификации.

## 5. Найденные и исправленные ошибки

Три ошибки выявились только при работе против живых систем.

**1. `DataCloneError: HTMLElement object could not be cloned`.**
`flush()` отправлял фону внутренние объекты очереди, в которых лежит DOM-элемент —
он нужен, чтобы позже обновить бейдж. Structured clone не умеет клонировать
`HTMLElement`, и сообщение падало. Исправлено: наружу уходит плоская проекция
`{id, domTitle, domBody}`, DOM-элементы остаются локально.

**2. Лента не классифицировалась, страница поста — работала.**
Различились два симптома, и оба оказались реальными дефектами, а не гипотезами:

- *Зависание фонового воркера.* Взрослый content script переживает перезапуск воркера.
  При разрыве порта ожидающие посты возвращались в очередь, но с обнулённой меткой
  времени, из-за чего сторожевой таймер мгновенно объявлял их «превышено 20 с» — хотя
  запрос прожил всего несколько сотен миллисекунд. Исправлено: посты убираются из
  состояния «в работе» перед повторной постановкой.
- *Зависание чтения тела ответа.* См. раздел 4.2.

Отдельно: первоначальная гипотеза о том, что причина — размере батча, **оказалась
неверной**. Измерения показали, что задержка архива случайна: одинаковый запрос
отвечал то за 1,5 с, то не отвечал 20 с. Первая правка (разбиение на батчи по 4 id)
снизила число запросов вдвое, но не устранила зависание. Ограничение на 20 id осталось
только для ограничения длины URL.

**3. `options.js` не работал.**
Переведён на тот же портовый транспорт, что и content script, по той же причине, что
в пункте 4.1.

## 6. Тесты

Четыре независимых набора, все зелёные на момент написания отчёта.

| Набор | Что проверяет | Результат |
|---|---|---|
| `api_model/smoke_test.py` | Модель, пакеты, воспроизводимость метрик | все проверки пройдены |
| `tools/test-background.js` | Сетевые сбои фона на поддельном `fetch` | 20 проверок пройдено |
| `tools/test-content.js` | Логика content script в jsdom | 43 проверки, 12 групп |
| `tools/dryrun.js` | Живой пайплайн целиком | OK |
| `tools/browser-check.js` | Реальный Chrome, 9 групп | все проверки пройдены |

**Проверенные сценарии отказов** (`test-background.js`) — те, что видны только против
живого сервиса и невидимы в прогоне по здоровому серверу:

- архив отдаёт заголовки и зависает на теле → отказ за 264 мс вместо зависания, посты
  классифицируются по тексту страницы, модель всё равно вызвана;
- тело ответа обрезано посередине объекта → один повтор, затем успех;
- один из нескольких запросов к архиву падает → посты из остальных chunks сохраняются;
- модель недоступна → результатов нет ни одного, метка **не выдумывается**, у каждого
  поста своя ошибка.

**Метрики модели:** accuracy **0,7106**, macro-F1 **0,6264** на 1600 отложенных постах.
Значения воспроизводятся ровно и совпадают с указанными в `metadata.json`.

**Фактический пайплайн** (8 постов, живой архив и живая модель):
`1,3 с`, из них `1 запрос к архиву + 1 запрос к модели`; повторный прогон целиком из
кэша — `25 мс`.

### Проверка, что тесты действительно ловят баги

Для регрессионных тестов проверено обратное: с временно возвращённой ошибкой
`test-background.js` падает на сценарии зависшего тела ответа, а `test-content.js` —
на сценарии перезапуска воркера. Тесты, которые проходят и с багом, бесполезны, поэтому
это проверялось явно.

## 7. Что осталось непроверенным

**Селекторы против живой разметки Reddit.** Reddit отдаёт анти-бот проверку
(«Prove your humanity»), поэтому автоматическая проверка против живого сайта невозможна.
Логика поиска постов покрыта тестами на фикстуре, повторяющей текущую разметку Reddit,
а вручную подтверждена в Firefox. Если Reddit поменяет разметку, сработает второй проход
поиска по пермалинкам.

## 8. Как запустить

```bash
# 1. запустить модель
python3 api_model/server.py --host 127.0.0.1 --port 8000

# 2. загрузить расширение
#    Firefox: about:debugging -> This Firefox -> Load Temporary Add-on -> manifest.json
#    Chrome:  chrome://extensions -> Режим разработчика -> Загрузить распакованное
```

Расширение работает только при запущенном локальном сервере — иначе бейджи покажут
`classifier offline`. Это ожидаемое поведение, метки не выдумываются.

## 9. Масштабирование

Схема рассчитана на личное использование. Кэш лежит в `chrome.storage.local`, то есть
принадлежит конкретному профилю браузера и **не разделяется между пользователями**.
Общего сервиса с готовыми метками в архитектуре нет.

Поэтому при тысяче пользователей, смотрящих один и тот же пост, классификация
выполнится тысячу раз. Модель детерминированная, поэтому метки совпадут — работа
получится избыточной, но не противоречивой. Умножатся и запросы к Arctic Shift, что
рискованно с точки зрения rate limit стороннего сервиса.

Если масштабирование станет задачей, точки приложения сил по возрастанию сложности:
серверный LRU-кэш по `id` (~15 строк, архитектуру не меняет) → общий индексатор с
пред-вычислением → приватно-общий кэш меток между расширениями.

По текущему решению задачи это не требуется.
