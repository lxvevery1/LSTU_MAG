Идея CI/CD чтобы всю деятельность оп билду + компоновке.

DEVELOP -> DELIVERY _> DEPLOY -> APP

нужен devops environment (platform).

runner - среда внутри которой исполняется деятельность по билду/delivery/deploy и не только.
Могут внутри выолнятся инструменты.
Простейший пример - runner - виртуалка с линуксом.
На раннерах выполняется последовательность инструкций, которые выполняют build, delivery, deploy.
Deploy для микросервисной (не одну программу, а кучу сервисов (бд, бэкенд, и тп)).

Рядом с devops платформой делается deploy environment.
deploy environment способен запускать то, что программное сообщество произвело.
Когда dev выполнят push с новым коммитом.
То devops платформа запустит процесс на свободном раннере.
Существует job. В Job'е есть шаги:
выоплняются последовательные операции, если step неудачный, то капут.
Job живет внутри runner.
Виртуальная машина не может быть раннером.
Раннеру передаюися указания
Дескриптор - то что делает job - это часть исходника. Написанный на одном из живых управления job'ами файл (yaml).
Есть 2 активных языка - из GitLab и
GitHub Actions - реализован во многих местах.

Devops положит в каждый проект Pipeline.
ПЛатформа не знает как собирать и деплоить программные компоненты.
Все отдается на откуп разраба пайплайна (девопс).

Developer -> commit -> push.
Исходники положились в репозиторий.

Hook вызывается (как ивент).
Hook - генерирует job, ставится раннер, действия из Job приводят к build(создание артефактов), delivery (доставка артефактов в место где их можно взять), deploy (артефакты разворачиваются в dev env).

Dev env предназначен для разработки и тестирования - dev/.

после push разрабы должны иметь доступ к обновленному билду.

Что есть в devops платформе.
Чтобы сделать source repo ничего не нужно - можно сделать сервер со своими home/ (без хуков, раннеров).

Логические объекты:
Артефакт REPO (тоже можно хранить в репозитории).

Что лежит в хранилище.

git repo - папка. В одном каталоге не может быть двух repo.
Могут быть подпроекты (в другой папке).
У каждого проекта своя папка.
Физически - репозиторий гит.
Логически - project.

Единица работы deva - одно приложение, компонент ввиде библиотеки или кусок сайта - должно быть выполнено в виде
законченного объекта папки с файлами - все это project.
Project - это некая организоавнная деятельность людей, которая имеет цель, время и этим занимается.
Строим дом - проект.
Основа Project - набор исходников, которые тупо валяются. Как кладовка или камод (лежит всякое).
Понятие проекта в Software не применяют временные рамки.

Чулан с исходниками - центральное понятие devops. (Project / Repository - по разному называется)

Есть много репозиториев, есть много account.
User - human being.
У одного user есть множество account.

Как связаны project и account?
У project есть owner - текущий владелец.
Доступ к project есть разный (3 уровня - read-only, write (право коммитить))
Защищенные ветки - право write разбивается на write м maintain.
maintain имеет право на write - + если есть защищенный branch, то maintainer умеет делать туда коммит.
4 уровень - админ может настраивать параметры проекта - связанные с правами доступа.
7 или 8 правил.

Owner по умолчанию админ.

Все проекты делятся на 3 категории - public / private / protected.
Public проект виден любому account платформы.
Protected означает: такие проекты могут видеть только зарегистрированные пользователи.
Protected часть будет видна только зарегистрированным.
Private проект - только для членов клуба (кому разрешено).

В гитлабе есть группы проектов - иерархия.
У каждого члена проектов есть membership (от членства зависят правила rw)

В Forgeio есть account -> organization -> team -> Project.
project привязан к организации (или нет).
Организация - компания. Все члены компании ассоциированы с организацией и по-умолчанию слово public означает что видят все проекты.
team - сгруппировать команды разработки. Полномочия на уровне team, accout, org.

Не нужно для каждого dev права. Назначил в нужную команду и все будет настроено автоматически.

Основная часть - таск трекер.

Работа разраба состоит в том, что реализует набор отдельных задач.
Он их выполняет. Для отслеживания кому какие задачи были выданы - таск трекер.
Для разраба таск трекер - рабочий инструмент - передается информация через таску.

Задачи могут быть связаны в сложную сеть.

Например, -> перекинуть таску другому разрабу (нарисовать что-нибудь дизайнеру).
Чат привязан к задаче.
Через таск трекер упрощает общение между разработчиками.
